# 3 - How MLOps Helps a Data Scientist

A Data Scientist is excellent at building models but usually works in isolation — notebooks on a laptop, manual steps, no reproducibility, and models saved as `model_final_v2_actually_final.pkl`. **MLOps brings software-engineering discipline (DevOps principles) to the machine-learning workflow** so that models reliably move from a laptop to production and stay healthy there.

## Core Ways MLOps Helps

### 1. Version Control (Git) + Best Practices
Without version control, a Data Scientist has no history of what changed, when, or why.

```
- Branching  → Multiple people experiment in parallel without breaking each
               other's work.
               e.g. one branch tries Random Forest, another tries XGBoost.
- RBAC       → (Role-Based Access Control) Only authorized people can merge to
               protected branches. A junior cannot push directly to `main`.
- Audit      → Every change is traceable — who changed what, when, and why.
               Critical for compliance (SOC2, etc.).
```

### 2. CI/CD for Automating the ML Lifecycle
Manually running setup → build → test → deploy on every change is slow and error-prone.

```
- CI (Continuous Integration)
    Runs automatically on every push:
      - Sets up the environment
      - Installs dependencies
      - Trains / builds the model
      - Runs tests (data validation, accuracy thresholds, etc.)

- CD (Continuous Deployment)
    Automatically ships the validated model to where it is served
    (API, cloud service, Kubernetes).
```

**Net effect:** the Data Scientist commits code, and the pipeline handles the repetitive engineering — freeing them to focus on the model itself.

## The Bigger Picture (Beyond Git + CI/CD)

Version control and CI/CD are the *entry point*. A complete MLOps practice adds more:

```
3. Containerization (Docker)   → Package model + dependencies + environment so it
                                 runs identically everywhere. Solves
                                 "works on my machine."

4. Model / Data Versioning     → Git handles CODE. Models & datasets are large
                                 binaries. Tools like DVC / MLflow version the
                                 datasets and model artifacts for reproducibility.

5. Experiment Tracking         → Hundreds of runs with different hyperparameters.
                                 MLflow / Weights & Biases log each run's params,
                                 metrics, and results.

6. Deployment & Serving        → Put the model behind a scalable API, often on
                                 Kubernetes; handle load and endpoint versioning.

7. Monitoring                  → Watch for:
                                   - Model drift (accuracy degrades over time)
                                   - Data drift (input distribution shifts)
                                   - Latency, errors, resource usage
                                 Feeds back into retraining — closing the loop.

8. Infrastructure as Code      → Terraform / Ansible to provision training and
                                 serving infra reproducibly.
```

### The Cleanest Way to Remember It
```
Data Scientist's world:  Data → Model → Metrics

MLOps wraps around it:   Version + Automate + Containerize + Deploy + Monitor
                                        │
                                        └──> (feedback) ──> Retrain
```

> **MLOps = DevOps principles + the two things ML adds that DevOps never had:**
> **data/model versioning** and **model monitoring (drift).**

# 4 - Hands-On: A Hello-World ML Model + First CI Pipeline

We took a tiny, reproducible ML project and wrote a **CI pipeline** that trains the model and stores the result as an artifact.

Reference repo: `iam-veeramalla/hello-world-mlops`

## The Project Structure

```
hello-world-mlops/
├── .github/workflows/      # CI pipeline definition (YAML)
├── artifacts/              # Output: model.pkl + metrics.json (created by train.py)
├── train.py                # Trains the model, writes artifacts/
├── run_model.py            # CLI: make a single prediction
├── app.py                  # Minimal Flask API serving /predict
├── Dockerfile              # Containerize the app
├── requirements.txt        # Python dependencies
└── README.md
```

### What Each Piece Does
```
- train.py    → Trains a small classifier on the classic Iris dataset
                (features = petal/sepal measurements). Writes:
                  - artifacts/model.pkl     (the serialized model)
                  - artifacts/metrics.json  (evaluation metrics)

- run_model.py→ Loads model.pkl and predicts from the command line:
                  python run_model.py --input "[5.1, 3.5, 1.4, 0.2]"

- app.py      → Serves the model over HTTP via a /predict endpoint:
                  curl -X POST http://127.0.0.1:5000/predict \
                       -H "Content-Type: application/json" \
                       -d '{"features":[5.1,3.5,1.4,0.2]}'
```

> The input `[5.1, 3.5, 1.4, 0.2]` is a single flower's four measurements — this
> ties directly back to the flower-classification example from Notes #1.

## The CI Pipeline

```yaml
name: CI - Train and Save the model
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  matrix-pip:
    name: Train and Save the model
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python: [3.11, 3.12]

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup python
        uses: actions/setup-python@v4
        with:
          python-version: ${{ matrix.python }}

      - name: Upgrade pip
        run: python -m pip install --upgrade pip setuptools wheel

      - name: Install project dependencies
        run: python -m pip install -r requirements.txt

      - name: Train the model
        run: |
          python train.py
          ls -la artifacts

      - name: Upload artifacts
        uses: actions/upload-artifact@v4
        with:
          name: ml-artifacts-${{ matrix.python }}-${{ github.run_id }}
          path: artifacts
```

### Line-by-Line Breakdown

```
on:                          # WHEN the pipeline runs
  push / pull_request        # On every push to main AND every PR targeting main.
  branches: [ main ]         # PRs let CI validate changes BEFORE they merge.

runs-on: ubuntu-latest       # The runner (fresh Ubuntu VM) GitHub provisions.

strategy.matrix:             # MATRIX BUILD — the key idea of this pipeline.
  python: [3.11, 3.12]       # Runs the ENTIRE job once per Python version, in
                             # parallel. Proves the model trains on BOTH 3.11
                             # and 3.12 → catches version-specific breakage early.
```

Then the **steps** (each runs in order inside the runner):

```
1. Checkout               → actions/checkout@v4 pulls your repo code into the runner.

2. Setup python           → actions/setup-python@v4 installs the Python version for
                            THIS matrix leg. ${{ matrix.python }} = 3.11 or 3.12.

3. Upgrade pip            → Fresh, modern build tooling (pip, setuptools, wheel)
                            to avoid dependency-install surprises.

4. Install dependencies   → Installs everything in requirements.txt (scikit-learn,
                            flask, etc.).

5. Train the model        → Runs train.py (creates artifacts/), then `ls -la artifacts`
                            to confirm model.pkl + metrics.json actually got written.
                            (A cheap sanity check inside CI.)

6. Upload artifacts       → actions/upload-artifact@v4 saves the artifacts/ folder so
                            you can DOWNLOAD the trained model from the GitHub Actions
                            run page. Without this, the model dies with the runner VM.
```

### Why the Artifact Name Is Built the Way It Is
```
name: ml-artifacts-${{ matrix.python }}-${{ github.run_id }}
                        │                    │
                        │                    └── unique per pipeline run
                        └── unique per Python version (3.11 vs 3.12)
```
This guarantees a **unique artifact name for every matrix leg of every run** — otherwise the two Python legs would collide on the same artifact name.

## How This Maps to the "MLOps Helps" Concepts

```
Concept from Notes #3            →  Where it shows up in this pipeline
--------------------------------    -------------------------------------------
Version control triggers CI      →  on: push / pull_request to main
CI automates setup               →  Setup python + Upgrade pip + Install deps
CI automates build/train         →  python train.py
CI automates a basic test        →  ls -la artifacts (verify outputs exist)
Reproducibility across envs      →  matrix: python [3.11, 3.12]
Model artifact handling          →  upload-artifact (the serialized model.pkl)
```

## Key Takeaways
```
- A matrix build tests the same job across multiple Python versions in parallel.
- CI should PRODUCE and PRESERVE the model artifact — training output that
  vanishes with the runner is useless.
- Always include a sanity check (ls -la artifacts) so a silently-failed train
  step doesn't pass as green.
- This is the "hello world" of MLOps CI: next steps typically add real tests,
  model/data versioning (DVC), containerization (the Dockerfile is already here),
  and deployment.
```
